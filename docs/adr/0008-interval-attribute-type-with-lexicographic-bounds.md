# `:interval` is an attribute kind with lexicographically comparable bounds

We want to link to all documents of a source within a page range, e.g. folio 12v to 15, including documents that only partly overlap the range. A document's position is stored as two free-form strings, `foliostart` and `Endseite`, such as `12v`, `13`, `281v-a` or `Av`. Neither existing mechanism fits. `:searchSpan` on `:number` compares one numeric attribute against a range, and `:normalization` redirects a search parameter to exactly one other attribute.

We introduced `:interval` as a dedicated attribute kind. Each value is a blank node carrying `view:lowerBound` and `view:upperBound`, matching the `:externalLink` blank-node pattern (ADR 0004). Without `:searchSpan`, a single search value matches the intervals that contain it. With `:searchSpan`, a search range matches the intervals that overlap it. Overlap is what the use case needs, and containment is the special case of a one-value range.

The bounds are compared as strings, not as numbers. The export writes them through `LexicographicMapper.makeLexicographicallySortable`. That function encodes each number with a unary length prefix (`9` → `0/9`, `10` → `00/10`), so the result sorts in natural order. We first considered converting everything to page numbers (`12r` → 23, `12v` → 24). We dropped that because the meaning of a bare number depends on the source: in a foliated source, `13` silently means `13r`, while in a paginated source it means page 13. Getting this right would have required knowing per source whether it is foliated. Searches are only issued from generated links, never typed by users, and they always filter by source too. So keys that sort consistently within one source are enough, and lexicographic keys give us that without any per-source knowledge.

The search input is normalized in the viewer by a JavaScript normalizer stored in the attribute's `:normalization`, applied to each bound separately. This duplicates the Scala mapper in JavaScript, and the two must produce identical keys or searches silently miss documents. We accepted this duplication over the alternative of having links carry pre-normalized keys, because it keeps links readable and lets hand-written links use folio numbers as they appear in the data. Both implementations live in the editor project, the JavaScript one in `definitions.ttl`, and a comment there points to the Scala original.

To support this, `:attribute` in `:normalization` became optional; without it the normalized value queries the attribute itself.
